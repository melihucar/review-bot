# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make build          # swift build (debug)
make run            # swift run ReviewBot (dev; launch-at-login only works from the packaged app)
make test           # swift test
make app            # scripts/build-app.sh → dist/Review Bot.app (ad-hoc signed by default)
make dmg VERSION=v1.2.3   # build the app, then package dist/ReviewBot-1.2.3.dmg (drag-to-install)
make clean          # swift package clean

swift test --filter VerdictTests              # run one test case/suite
swift test --filter ReviewEngineFeatureTests  # run the mocked end-to-end workflow tests
```

Signed/notarizable build: `CODE_SIGN_IDENTITY="Developer ID Application: …" make app`.

CI/release: `.github/workflows/ci.yml` runs build + test on every push/PR. `.github/workflows/release.yml` fires on a `v*` tag — it builds the DMG and publishes a GitHub Release. `APP_VERSION` (set to the tag) is stamped into `CFBundleShortVersionString` by `build-app.sh` **before** signing so the ad-hoc signature stays valid; the version is also the DMG filename. The Release body is extracted from the matching `## [<version>]` section of `CHANGELOG.md`; the workflow **fails** if that section is missing, so the changelog must be updated before tagging.

Note: `Package.swift` uses swift-tools 6.0 but pins **Swift 5 language mode**, so strict concurrency checks are relaxed even though the code uses actors/`@MainActor`.

## Architecture

A macOS menu-bar app (`MenuBarExtra`, `LSUIElement` accessory — no Dock icon) that reviews GitHub PRs. GitHub access is always the developer's already-authenticated `gh`; reviewers are the `claude`, `codex` and `opencode` CLIs (using their own logins or config by default) plus DeepSeek over HTTP. `ReviewerName`'s declaration order — claude, codex, opencode, deepseek — is load-bearing, not cosmetic: `enabledReviewers` derives from `allCases`, so it fixes the panel order in the posted review and the reconciliation adjudicator preference. DeepSeek is last precisely so it never becomes the adjudicator. Every reviewer, opencode included, is configured by the same `ReviewerConfiguration` (enabled, model, effort, `authMode`), so `enabledReviewers`, `settings(for:)` and `meteredUsage` can treat them uniformly. **Nothing secret lands in `config.json`** — when a reviewer is configured for API-key auth, the key lives in the login Keychain (`CredentialStore.swift`, `CredentialStoring` protocol with a `KeychainCredentialStore` and an `InMemoryCredentialStore` for tests) and only `authMode` is persisted.

`apiKey(for:)` consults `ReviewerName.apiKeyOverrideEnvironmentVariable` **before** the Keychain. That one is *inbound* and total — every reviewer has a distinct value, which `CredentialStoreTests` asserts — unlike the *outbound* `apiKeyEnvironmentVariable` that is handed to a CLI child process and is `nil` for DeepSeek (no CLI) and for opencode (it authenticates through its own config, not a key). Where both exist they deliberately name the same variable, so a key saved under one name is never forwarded under another. opencode is the one reviewer with no key path at all: `supportsAPIKeyAuth` is false for it, so `ReviewerCard` hides the sign-in picker, the decoder pins it to `.session`, and its `OPENCODE_API_KEY` override is inert — it exists only to keep the switch total and distinct. The override only helps a shell-launched run — started from Finder or at login the app inherits launchd's environment — so it is a development affordance, not the packaged app's path. Because it can shadow a saved key, `AppModel.saveAPIKey`/`removeAPIKey` compare what resolves after the write and say so rather than reporting a save or removal that is not the value in effect.

**Nothing may call `apiKey(for:)` directly.** It is a synchronous `SecItemCopyMatching`, and on an ad-hoc-signed build it blocks its thread on a modal Keychain prompt until the user answers — on an actor's executor that stalls every task that actor is running, and on the main actor it freezes the window that asked. Both callers go through `ResolvedCredentials.resolve`, which reads on a detached task: `ReviewEngine.review` resolves the keys of every *enabled, key-mode* reviewer once, before the reviewers fan out, and threads the resulting `ResolvedCredentials` through `runReviewers` → `runReviewerOnce` → each `run…` method and through `runReconciliation`; `AppModel.refreshSavedKeys` is `async` for the same reason, and `saveAPIKey`/`removeAPIKey` read back what the write left in effect on the same detached task that performed it. Resolving up front also means one prompt per reviewer per review rather than one for the missing-key check and another for the injection.

**The post-rebuild Keychain prompt is fixable only with a team-signed identity — two cheaper approaches were measured and both fail.** Every item carries a *partition list* alongside its ACL, checked independently, and it is stamped `cdhash:<saving binary>` whenever the signature has no team identity. So (1) `kSecAttrAccess` with a nil application list ("any app, never ask") does not help — the partition check still refuses a rebuilt binary; and (2) a self-signed identity does not either — it fixes the ACL requirement (`identifier "…" and certificate leaf = H"…"`, which a rebuild satisfies) but the partition list stays `cdhash:` because the cert has no team id. Only `CODE_SIGN_IDENTITY="Developer ID Application: …" make app` makes the partition `teamid:` and therefore stable. `CredentialStore.swift` carries both negative results as a comment where the code would go.

**Everything runs through `ProcessRunner` (`CommandRunning` protocol), never a shell.** Commands are argument arrays (no interpolation into a shell string). `ProcessRunner` wraps each command in `perl -e 'alarm …; exec'` for a hard timeout, and augments `PATH` so GUI-launched processes find the CLIs. Because a Finder-/launch-at-login-started app inherits launchd's minimal `PATH` (not the shell's), `ProcessRunner.augmentedPath` probes the login+interactive shell once at first use (`$SHELL -ilc`, behind a sentinel + `perl alarm` timeout) to recover the real `PATH` — this is what makes version-manager installs (nvm/mise/volta/fnm/asdf) resolvable — then falls back to a fixed list of common install dirs (Homebrew, `~/.local/bin`, `~/.npm-global/bin`) and the inherited value. The pure merge step is `ProcessRunner.composePATH` (unit-tested in `ProcessRunnerTests`). `run` also takes `EnvironmentOverrides` (`[String: String?]`, a `nil` value **removes** the variable) — this is how an API key is handed to a CLI reviewer, how session-auth mode unsets an inherited one, and how opencode receives `OPENCODE_CONFIG_DIR`/`OPENCODE_CONFIG_CONTENT`. The protocol is the seam for testing — inject a mock `CommandRunning` to exercise the whole workflow without touching GitHub or an AI provider (see `ReviewEngineFeatureTests`).

**DeepSeek is the one reviewer that is not a CLI.** `DeepSeekClient` (`ChatCompleting` protocol — the injectable seam) posts to the OpenAI-compatible `chat/completions` endpoint, and `DeepSeekReviewer` runs the agent loop that the other CLIs run internally: offer `WorktreeTools.definitions`, execute each returned tool call locally, feed the result back, repeat.

**Never treat "no tool calls" as "finished".** DeepSeek returns no `reasoning_content` field, so its thinking and its answer share `content` — a tool-call-free turn is just as likely to be mid-investigation narration, and posting it sends a monologue to GitHub (this happened). When the model stops calling tools, that turn is accepted only if `followsContract` says it already has the contract's structure; otherwise `requestFinalReview` sends `DefaultPrompt.finalReviewRequest` with `tools: nil` and uses that reply. The round cap and the wall-clock budget take the same path. `trimmedToContract` is the backstop for a leftover preamble and deliberately matches loose heading variants. `WorktreeTools` is the read-only sandbox — every path is resolved (symlinks included) and refused unless it stays inside the review worktree. Its size limit bounds what a read *returns*, never whether a file can be opened: `read_file` pages with `offset`/`limit` and `search` matches line by line, so a diff far larger than any single response is still fully reachable. Refusing a large file outright — and, worse, reporting it as unreadable text — left a reviewer convinced the pull request could not be reviewed at all. A model that rejects `tools` (reasoning models do) surfaces as `ChatCompletionError.toolsUnsupported`, and the reviewer retries once without them; the diff, the thread and the merge preview are inlined in the opening message so that fallback still works. Inlining the merge preview is the part that is easy to forget: `WorktreeTools` will serve `.review-bot-merge.md` if the model asks, but on the tools-unsupported path there are no tools at all, so without it the review contract is telling DeepSeek to consult evidence it cannot reach.

**Layers:**
- `ReviewBotApp` → `MenuBarView` (popover) / `DashboardView` (settings window). `AppModel` (`@MainActor` `ObservableObject`) owns UI state and a 2-second scheduler loop that fires `ReviewEngine.poll` when the poll interval elapses (unless paused). "Run now" polls even while paused.
- `ReviewEngine` (`actor`) is the core workflow — discovery, worktree prep, running reviewers, aggregation, submission. See flow below. Its `init` seams all have production defaults: `runner` (`CommandRunning`), `credentials` (`CredentialStoring`, so a test never touches the developer's Keychain), `chatClient` (`ChatCompleting` — without it a DeepSeek test hits the real API) and `now` (`@Sendable () -> Date`, which drives `ReviewAttemptStore` and `RetryPolicy`, so the backoff tests cannot run without it).
- `Storage.swift` holds the persistence types: `StoragePaths` (all files under `~/Library/Application Support/ReviewBot/`), `SettingsStore` (auto-saves `config.json` on every mutation via `didSet`), `HistoryStore` (`history.json`, capped 2,000), `ReviewedStateStore` (`reviewed.json` dedup keys), and `ActivityLogger` (daily logs).

**Review flow (`ReviewEngine.poll` → `discoverPendingReviews` → `runPendingReviews` → `review`):**
1. `gh search prs --review-requested=@me` per enabled repo, then `gh pr view` for metadata.
2. Dedup key = `slug#number@headRefOid@requestMarker`, where `requestMarker` is the timestamp of the latest `review_requested` timeline event. It falls back to the head OID **only when the timeline genuinely has no such event** — a *failed* lookup throws instead, because the head OID is usually a key an earlier review already recorded, so falling back on failure silently swallowed re-requests at the same commit (issue #6). A pull request that can't be inspected is reported as a failure and retried, under the same budget as a failing review.
3. `git worktree add --detach` at the PR head under `worktrees/`; write `.review-bot-diff.patch` and `.review-bot-thread.md` (PR conversation + reviews + inline comments) into it.
4. Load trusted `REVIEW.md` via `git show <baseRefOid>:REVIEW.md` — **from the base commit, so a PR can't weaken its own review rules.**
5. Run enabled reviewers **in parallel** (a task group over `ReviewBotConfiguration.enabledReviewers`, re-sorted so output order is stable — never a hardcoded tuple array, which is how a newly added reviewer gets counted by `enabledReviewers` and `meteredUsage` yet never actually runs), each read-only (`claude --allowedTools Read Grep Glob`; `codex exec -s read-only`; `opencode run` under a dedicated deny-all-except-read/grep/glob agent injected via `OPENCODE_CONFIG_DIR` + `OPENCODE_CONFIG_CONTENT`, with `--pure`; DeepSeek in-process behind `WorktreeTools`), 900s timeout — the CLIs get theirs from `ProcessRunner`'s alarm; DeepSeek has two bounds, and they must not be equal. `DeepSeekReviewer.defaultReviewSeconds` (900s) is the one meant to fire, because reaching it ends the loop by *asking for the review* rather than throwing a dozen paid rounds away, while `runDeepSeek` races the loop against a hard stop set to that plus `deepSeekClosingRequestMargin` — derived from the reviewer's constant so the two cannot drift back into a tie, and wide enough for the closing request the graceful exit still has to make. Both DeepSeek timeout paths must set `ReviewerResult.timedOut`, or the retry below answers a hung agent loop with a second one: the hard stop sets it by hand, and `failedReviewer(_:_:error:)` sets it for a provider timeout after unwrapping `PartialSpendFailure` — `ChatCompletionError.timedOut`, not `URLError.timedOut`, is what actually arrives, since `DeepSeekClient` converts it. A reviewer that fails or returns no verdict is **run once more within the same review**: `ReviewEngine.runReviewer` is the retry wrapper, and it sits above `runReviewerOnce`, whose `switch` over `reviewer.name` is the one compile-time guarantee that every reviewer is dispatched — `missingCredential` is checked there, once, rather than in each `run…` method, because reconciliation now goes through the same dispatch. The worktree and context are already prepared, so the retry costs one invocation instead of the whole pipeline. Two exceptions, both because the second call cannot plausibly differ: a **timeout** (re-running a hung CLI would just spend its 900s again) and a **terminal failure** — exhausted quota, rejected credential, unusable model — classified by `ReviewerFailureClass.classify` from the reviewer's own message, or from `missingCredential`'s when a reviewer is set to API-key auth and its key cannot be read — that one fails identically however often it is called, and only a settings change fixes it. That classifier is deliberately conservative: anything unrecognised stays retryable, since mistaking a recoverable failure for a terminal one silently drops a reviewer, while the reverse costs one call the retry already budgeted for. **For DeepSeek that retry is a second full agent loop and real money**, which is why the terminal markers cover its wording too: `ChatCompletionError.http` 401/402 text alongside the CLIs' quota and login phrases.
6. Each reviewer must emit a trailing `VERDICT: BLOCKING|SHOULD_FIX|NITS_ONLY|CLEAN` line (`VerdictParser`). `DecisionEvaluator` takes the **strictest** verdict among the reviewers that produced one: any `SHOULD_FIX`+ → request changes, otherwise the strictest configured action. **A reviewer that failed contributes nothing rather than forcing a neutral comment** — the panel decides on its survivors, and `aggregateReview` names the missing reviewer and its failure in the posted body so a partial panel is never mistaken for a unanimous one. Holding the whole review hostage to one CLI meant a provider outage discarded the other reviewer's completed work on every poll until the failure budget abandoned the request. With **no** reviewer producing a verdict there is nothing to decide, so `ReviewEngine` posts nothing and leaves the request for the next poll (`DecisionEvaluator.evaluate` returns `.comment` there, and must never approve on an empty set).
7. **Reconciliation:** when two reviewers parsed verdicts that straddle the gate (`DecisionEvaluator.gateDisagreement` — one `SHOULD_FIX`+ while the other clears it), `runReconciliation` runs one more read-only pass with `DefaultPrompt.reconciliation`, feeding it both reviews to re-check each gating finding for substance and scope. The adjudicator is the first *enabled* reviewer in `ReviewerName` declaration order — Claude, then Codex, then opencode — expressed over `enabledReviewers` and guarded when none qualifies, never an if-ladder ending in an unconditional `runOpencode`, which would spawn a disabled CLI on a DeepSeek-only panel. DeepSeek never adjudicates: it is the reviewer that always bills a key, and giving the last word to an extra metered pass is the wrong default. Its verdict (via `DecisionEvaluator.decision(for:)`) becomes the decision; if the adjudicator fails or emits no verdict, fall back to the strictest. This keeps a single reviewer's false blocker from gating a correct PR. The reconciliation is disclosed in the posted Markdown.
8. Collect usage: `TokenUsage` per reviewer, summed across every provider call, plus the reconciliation pass, which `meteredUsage` credits to whichever reviewer adjudicated. Claude's comes from its `--output-format json` envelope (`claudeOutput` falls back to treating stdout as the review if that envelope is absent, which is what keeps the mocked tests and any CLI that accepts the flag but prints text working — the flag itself is passed unconditionally, so a CLI that *rejects* it fails rather than falling back); DeepSeek's comes from each response's `usage` object, which carries token counts and no price, so a DeepSeek review reports tokens with an unknown cost rather than a fabricated `$0.00`. Codex and opencode report nothing (`reportsTokenUsage` is an explicit switch per reviewer, not a negation of the cases that happen to report nothing today). **Only `authMode == .apiKey` reviewers are metered** — a session CLI's cost is a subscription, so `meteredUsage` excludes it, which covers opencode in every configuration since it has no key mode. Four under-counts are easy to reintroduce, all the same mistake — *a call that came back useless was still billed*: (a) `failedReviewer` must carry a failed attempt's `usage`, since a failure is the dominant trigger for the in-review retry; (b) that retry must **accumulate** usage across attempts rather than let the second result replace the first; (c) a reconciliation that produced no verdict is still metered, which is why `review` keeps `adjudicationSpend` separate from the `adjudication` that decided the review; and (d) a DeepSeek loop that fails after paid rounds throws `DeepSeekReviewer.PartialSpendFailure`, so `runDeepSeek` must unwrap it with `DeepSeekReviewer.outcome(of:)` rather than reporting a failure with no usage. `spent` is assigned before the incomplete-review throw for the same reason. The total always lands in the `HistoryEntry`; `includeUsageInReview` only controls whether `usageReport` appends it to the posted Markdown.
9. Aggregate to Markdown, save under `reviews/`, submit with `gh pr review`. **Only after GitHub accepts** is the dedup key persisted and the worktree removed — so a failed post is retried on the next poll.

**Concurrent reviews.** `runPendingReviews` runs the discovered requests through a bounded `withTaskGroup`, `configuration.maxConcurrentReviews` at a time (default 3; `1` is the old sequential poll). The cap matters because each pull request runs *every* enabled reviewer. Concurrency is safe for the stores (`ReviewedStateStore`, `ReviewAttemptStore`, `LastReviewedStore`) because `ReviewEngine` is an actor and they are only touched from it — but **git is not**: pull requests in the same repository share one clone, so `checkOutPullRequest` (fetch + `worktree add`) and the worktree cleanup are serialized per slug by `RepositoryGate`, a small FIFO mutex. Its `acquire` must be paired with a `release` on *every* path, including the throwing one, or the rest of that repository's reviews stall for the poll. The status line is single-valued, so a queue of reviews reports aggregate progress from `runPendingReviews` and `review` narrates itself only when it is the only one (`announcesStatus`).

**Bounded retries.** Because a review that never posts leaves its dedup key unwritten, that retry needs a bound or a permanently broken reviewer re-runs the pipeline on every poll forever. `ReviewAttemptStore` (`attempts.json`) counts consecutive failures per key, and the pure `RetryPolicy` turns (attempt, budget, poll interval, now) into `run` / `backOff(remaining:)` / `exhausted(failures:)`: the first retry is immediate, then the added gap doubles (0, 1×, 3×, 7×, 15× the poll interval, capped at 4h), and the request is abandoned once it hits `configuration.failureBudget` (default 5). A posted review clears the count; a new commit or re-request keys a fresh request. **"Run now" passes `manual: true`, which ignores both the backoff and the budget** — that is the in-app reset once the underlying breakage is fixed. Requests skipped this way are counted into the status line so a paused request is never silently invisible.

**Prompt composition:** `DefaultPrompt.combined(with: customPrompt, repositoryRules:)` layers the built-in review contract + global custom prompt + per-repo `REVIEW.md`. The contract enforces a **scope gate**: a finding may only be `BLOCKING`/`SHOULD_FIX` if its `path:line` is a line the diff adds/changes; pre-existing, out-of-diff, and third-party/vendored code are notes at most. `DefaultPrompt.reconciliation` reuses the same scope discipline when adjudicating.

## Notes for changes

- **Always update `CHANGELOG.md` in the same change.** Whenever you implement, change, fix, or remove anything, add a bullet under `## [Unreleased]` in the correct group (`Added` / `Changed` / `Fixed` / `Removed`), following [Keep a Changelog](https://keepachangelog.com/). Releases derive their GitHub Release notes from the matching version section, and `release.yml` fails the release if a tag has no `## [<version>]` entry. To cut a release: rename `## [Unreleased]` to `## [<version>] - <YYYY-MM-DD>`, add a fresh empty `## [Unreleased]`, update the compare links at the bottom, then tag `v<version>`.
- Adding a reviewer: extend `ReviewerName` — mind where you put the case, since declaration order fixes panel order and adjudicator preference — and every one of its switches (`commandName`, `apiKeyEnvironmentVariable`, `apiKeyOverrideEnvironmentVariable`, `usesEffortSetting`, `reportsTokenUsage`, `efforts`, `symbolName`), all of which are total. Add a stored `ReviewerConfiguration` to `ReviewBotConfiguration` with defensive decoding plus a `settings(for:)` case, add a `run…` method in `ReviewEngine` taking the review's `ResolvedCredentials`, and add a case in `runReviewerOnce`'s dispatch — the single door the panel and the adjudicator both go through, which is where `missingCredential` guards every reviewer. `ReviewersSettingsView`, `enabledReviewers`, `reviewerDescription` and the `poll` guard all pick it up from `ReviewerName.allCases`/`enabledReviewers` automatically, so `runReviewerOnce`'s switch is the only place that has to name it. Keep the read-only sandbox flags: `opencode` also needs its sandbox agent file (`ReviewEngine.ensureOpencodeAgent`) and hands its config through the `CommandRunning` environment-override seam added in `ProcessRunner`, and a non-CLI reviewer needs a `WorktreeTools`-equivalent sandbox of its own plus a terminal-failure marker so its credential errors do not burn the retry budget.
- The settings window is created manually as an `NSWindow` (not SwiftUI `Settings` scene). Because the app is an accessory, `openSettings()` must promote the app to `.setActivationPolicy(.regular)` to bring the window forward, and revert to `.accessory` on close.
- Config decoding is defensive (`decodeIfPresent` with defaults) to survive schema migrations — preserve that when adding fields.
